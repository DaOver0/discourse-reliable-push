# Проверка архива Reliable Push 0.3.0

Дата статической проверки: **2026-07-21**.

## Выполнено успешно

- синтаксис всех Ruby-файлов: `ruby -c`;
- разбор `config/settings.yml` и обеих locale YAML;
- синтаксис клиентского initializer и service-worker: `node --check`;
- проверка всех локальных путей загрузки из `plugin.rb`;
- проверка уникальности классов миграций;
- проверка, что все прямо и динамически используемые `reliable_push_*` site settings объявлены;
- поиск незавершённых маркеров `TODO`, `FIXME`, `XXX`;
- проверка целостности ZIP через `unzip -t` выполняется после упаковки.

## Что покрывают добавленные regression specs

- semantic dedupe обычного поста и персонального уведомления;
- повышение приоритета и восстановление failed-доставки;
- монотонность `accepted/received/opened`;
- несколько браузерных подписок одного пользователя;
- безопасное переназначение endpoint при явной клиентской синхронизации;
- запрет фонового core-mirroring отбирать endpoint у другого пользователя;
- mute/ACL и исключение автора;
- fanout обычных сообщений темы;
- защита административного status endpoint.

## Что в этой среде не запускалось

Полный `bundle exec rspec`, миграции и end-to-end Web Push не запускались, поскольку для них необходимы совместимый checkout Discourse, PostgreSQL, Redis/Sidekiq, VAPID-конфигурация, браузерная Push-подписка и установленные версии Chat/Resenha.

Перед включением полной замены core sender разверните плагин с:

```text
reliable_push_replace_core_web_push = false
```

Проверьте состояния `accepted` и `received` на тестовых пользователях, затем включайте замену.

## Гарантии доставки

Реализация использует durable outbox, повторные попытки, атомарные state claims и восстановление потерянной постановки jobs. Это модель **at-least-once**, а не exactly-once: если Push-сервис фактически принял запрос, но HTTP-ответ потерялся, повторная отправка теоретически возможна.
