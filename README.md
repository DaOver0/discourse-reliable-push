# discourse-reliable-push

**Version 0.1.0 — Discourse 2026.10 PWA Web Push registration health and recovery**

> Status: source-checked implementation, **not yet end-to-end validated on a running Discourse 2026.10 installation or physical iOS/Android devices**. Deploy to staging first. This release is not a guaranteed-delivery system.

This plugin supplements (but **does not replace**) the built-in Discourse Web Push pipeline. Its goal is to make **installed PWA push registration** observable, recover previous consent-based subscriptions after a browser/worker restart, and send a per-device diagnostic notification.

### What works in 0.1.0

- Checks platform support, system Notification permission, Discourse Service Worker readiness, a local subscription, and the server registration.
- Detects an activated Service Worker even when it has not yet claimed the initial PWA page (`navigator.serviceWorker.controller` may be null).
- Idempotently synchronizes an existing subscription with **the authenticated Discourse user** via a plugin route, addressing missing server records.
- If a user **previously enabled** Web Push and allowed system notifications, optionally recreates a missing subscription on app reopen. It never opens permission prompts automatically.
- Respects explicit push disable actions in Discourse (the native per-user disabled marker); does **not** enable push after the user switched it off.
- Displays status and action buttons in the **user's own** Preferences → Notifications → Desktop notifications section.
- Provides a rate-limited, background-job test push to **this browser's subscription only**; the result is reported as *queued*, not *delivered*.
- Russian and English client/admin strings.
- No external notification server, VAPID key rotation, new Service Worker, database migrations, or monkey-patches.

### Forum and Chat

Notifications for topics, mentions, PMs, Discourse Chat channels, direct messages and watched chat threads are generated by **Discourse/Chat**, not this plugin. `discourse-reliable-push` keeps those notifications able to reach correctly registered PWA subscriptions, **subject to Discourse/Chat's existing policies** (global push level, channel `always`/`mention`/`never`, mute, user presence, push time window, DND, browser permissions).

**Scope limit:** v0.1.0 does **not** independently produce a push for every Chat message or change watched-thread push semantics. If core does not create a push event, this plugin does not invent one. This is necessary to avoid flooding and privacy regressions.

### Not implemented in 0.1.0

- Managed server-side delivery outbox, retries, delivery acknowledgements, statistics dashboard (planned 0.2.0).
- Custom notifications on Voice room join (planned, opt-in, 0.3.0).
- Browser/device fingerprinting or remote device administration.

### Compatibility and prerequisites

- Intended for Discourse **v2026.10** with the modern `.gjs` frontend plugin conventions. Source APIs verified against Discourse upstream `main` (October 2026); the exact instance commit remains unverified.
- Standard, healthy Discourse Web Push and VAPID configuration; **HTTPS**, correct Service Worker, Sidekiq, outbound HTTPS to platform push providers.
- iOS: the site must be **installed as a PWA on the Home Screen** (iOS 16.4+). Permissions must be granted by the user. Android: Web Push-capable installed PWA.
- Native Discourse Chat must be enabled if Chat alerts are desired.

### Install

Clone the repository into Discourse's **`plugins`** directory using the normal Docker `after_code` hook (example below). Installation or updates involving a new plugin need **`./launcher rebuild app`**, not merely `./launcher restart app`.

```yaml
hooks:
  after_code:
    - exec:
        cd: $home/plugins
        cmd:
          - git clone https://github.com/OWNER/discourse-reliable-push.git
```

Replace `OWNER` with your GitHub owner. **Add the `git clone` line to the existing `after_code` block; do not replace your other plugins or duplicate the YAML key.** If the repository is already cloned during deploy, adapt the hook to avoid a second clone.

```sh
cd /var/discourse
./launcher rebuild app
```

In site settings, search for `reliable_push`. Ensure `reliable_push_enabled` is on. The native Discourse push site settings and VAPID credentials must also be configured. From an installed PWA, visit your own **Preferences → Notifications** and use **Enable on this device** / **Check again** and **Send test push**.

### How the subscription repair works

1. App starts, checks `Notification.permission` and whether the existing Discourse Service Worker is ready.
2. If push is explicitly switched off in Discourse, no sync/repair occurs.
3. If a subscription exists, the plugin posts its public PushSubscription envelope to an authenticated route and core stores it.
4. If it does not exist but core's per-user marker says `subscribed`, permission is `granted`, and auto-repair is enabled, the plugin attempts to resubscribe with **existing core VAPID key**. Failure is displayed without retry loops.
5. User may explicitly enable/re-enable notifications by clicking the button. Browser permission is requested **only on click**.
6. Test push is sent by Sidekiq through the installed Web Push gem, directly to the selected subscription.

#### API (authenticated, CSRF-protected by Discourse)

All requests include `subscription[endpoint]`, `subscription[keys][p256dh]`, and `subscription[keys][auth]` in the POST body. Endpoints/keys are never returned in response JSON.

| Path | Effect |
|---|---|
| `POST /reliable-push/status` | Read-only check of exact subscription ownership |
| `POST /reliable-push/sync` | Store/repair exact subscription using Discourse core |
| `POST /reliable-push/test` | Queue rate-limited Web Push to this authenticated user's exact subscription |

Response format: `{ "registered": true/false }` for `status` and `sync`, `{ "queued": true }` for `test`.

### Config

| Site setting | Default | Description |
|---|---|---|
| `reliable_push_enabled` | `true` | Enable plugin |
| `reliable_push_auto_repair` | `true` | Repair **previously opted-in** subscription in granted-permission context |
| `reliable_push_test_notifications` | `true` | Allow user-initiated targeted diagnostic push |

### Security

- All server endpoints require an authenticated session; test is rate-limited to two per minute per user.
- The server selects the subscription only from `current_user.push_subscriptions`. Cross-account exact duplicate subscriptions are moved to the newly authenticated user on `/sync` to mitigate shared-device leakage.
- No stored notification audit messages or additional database tables are created.
- No push permission prompt is triggered automatically, and no attempts are made to override OS settings.
- A queued/HTTP 2xx Web Push cannot prove that iOS/Android showed the notification.

### Troubleshooting

- **No buttons:** check plugin is enabled, navigate to **your own** profile preferences, and ensure you are not using a wrapped app webview.
- **Worker not ready:** reopen PWA; verify HTTPS and that `/service-worker.js` is available within the site's base path.
- **Missing VAPID:** verify Discourse's native push configuration.
- **Test queued but not received:** check Sidekiq/logs, push provider access, Focus/DND, system app permissions, device online state.
- **Forum works but Chat doesn't:** check the global push notification level, chat membership notification level, muted channels, and native Chat notification creation. This plugin does not override Chat policy.
- **Native push disabled:** use the plugin's explicit enable button; it will never override an intentional Discourse disable in the background.
- **Changing user in same PWA:** open the PWA under the new account so the subscription transfers. Do not rely on concurrent accounts in multiple tabs within the same browser profile.
